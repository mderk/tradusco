## Что есть сейчас

`TranslationProject` строится с одним `dst_language` (`lib/TranslationProject.py:54`)
и держит его как поле. От него зависит всё: колонка CSV (`row[self.dst_language]`),
файл `progress.json` (`storage.load_progress(project_id, dst_language)`), файл
правил `<lang>/context.txt`, запись отказов (`append_failure`), колонка
`context_<lang>`. Ответ модели — плоский список строк в порядке фраз
(`TranslationsResponse.translations: list[str]`, `lib/contracts/translation_contracts.py:11`).
Прогон на N языков — это N процессов, каждый заново читает исходник.

36 упоминаний `dst_language` в рабочем коде, ещё около сорока в тестах.

## Целевое поведение

Один прогон принимает список языков. Один запрос к модели переводит батч фраз
сразу на все языки прогона. Ответ раскладывается по языкам; форматы файлов на
диске не меняются — `progress.json` остаётся по языку, CSV остаётся с колонкой
на язык.

Отказ по одному языку стоит одного языка. Сейчас отказ батча стоит батча — при
одном языке это одно и то же, при двадцати разница принципиальная.

## Контракт ответа

Плоский список заменяется списком блоков по языку:

```python
class LanguageTranslations(BaseModel):
    model_config = ConfigDict(extra="forbid")
    language: str
    translations: list[str]

class TranslationsResponse(BaseModel):
    model_config = ConfigDict(extra="forbid")
    translations: list[LanguageTranslations]
```

Именно список объектов, а не `dict[str, list[str]]`: под `strict: true`
Structured Outputs не принимает объект с произвольными ключами, а язык прогона —
это как раз произвольный ключ. Схема уходит в запрос через
`BaseDriver.get_structured_output_schema()` (`lib/llm/BaseDriver.py:49`), менять
там ничего не надо — она берёт `model_json_schema()` от этой же модели.

Разбор ответа проверяет по каждому блоку:

- `language` есть в языках прогона — иначе блок отбрасывается;
- длина `translations` равна числу фраз батча — иначе язык считается отказавшим;
- язык прогона, для которого блока нет, считается отказавшим.

Отказавший язык не мешает остальным: его фразы уходят в `append_failure` под его
собственным кодом, остальные языки сохраняются как обычно.

Для метода `standard` (без Structured Outputs) `prompts/output_format.txt`
переписывается под ту же форму. Разбор общий, различается только источник JSON.

## Состав батча

Фразы, которым нужен перевод, у разных языков разные: где-то колонка уже
заполнена, где-то нет. Правило: батч набирается объединением — фраза попадает в
запрос, если её не хватает хотя бы одному языку прогона. При раскладке ответа
фраза применяется только к тем языкам, которым её недоставало; уже валидное
значение чужой перевод не затирает. При `--regenerate` не хватает всем, и
объединение вырождается в полный список.

Проверки, которые сейчас идут по одному языку (валидность текста, плейсхолдеры),
идут по каждому языку отдельно. Строка, забракованная в польском, остаётся в
корейском.

## Изменения по файлам

### `lib/contracts/translation_contracts.py`

Новая форма ответа, см. выше.

### `lib/TranslationTool.py`

- `Input` (строка 113): `dst_language: str` → `dst_languages: list[LanguageRef]`,
  где `LanguageRef` несёт код и название (`ru`, `Russian`). Сейчас в промпт уходит
  `dst_language.upper()` (строка 184), из-за чего `uk` читается моделью как United
  Kingdom — со списком эта строка переписывается всё равно, поэтому дефект
  закрывается здесь, а не в A5.
- `create_prompt`, `translate_standard`, `translate_structured`, `translate_function`,
  `setup` — параметр `dst_language` → `dst_languages` по всей цепочке.
- `merge_translations` возвращает `dict[str, dict[str, str]]`: язык → фраза →
  перевод.

### `lib/PromptManager.py`

`_required_vars["translation"]` → `{"base_language", "dst_languages", "phrases_json"}`.

Отдельно чинится ловушка, иначе рассинхрон промпта и модели останется незаметным:
`load_prompt` при провале валидации под `strict_validation` возвращает пустую
строку, и прогон молча уезжает на дефолтный промпт. Должен падать.

### `prompts/translation.txt`, `prompts/output_format.txt`

`{dst_language}` → перечисление языков прогона с кодом и названием. Требование
«вернуть переводы в том же порядке» становится требованием вернуть блок на каждый
язык, в каждом блоке — порядок входных фраз.

### `lib/TranslationProject.py`

- поле `dst_language: str` → `dst_languages: list[str]`; проверка вхождения в
  `config.languages` — по каждому;
- `_load_context` собирает `<lang>/context.txt` по всем языкам прогона, каждый под
  меткой своей локали (полностью слот доводится в A5);
- `_translate_pass`: `progress` становится `dict[lang, dict[str, str]]`,
  `csv_corrections` — `dict[lang, set[str]]`; условие «фразу надо переводить»
  считается по объединению языков;
- `_apply_translated_batch` раскладывает ответ по языкам, валидирует каждый
  отдельно, пишет в `row[lang]` и в `progress[lang]`;
- `_record_failure` / `_record_batch_failures` получают язык параметром;
- `_process_translation_batch` возвращает `dict[lang, dict[str, str]]`, `None`
  только если отказал весь запрос;
- `_has_missing_phrases` и добивочный проход по fallback-модели считаются по
  каждому языку.

### `lib/storage/`

`set_active_language` одноязычный, а от него зависят и `save_progress`, и
слияние колонок в `save_translations`. Вводится `set_active_languages(list[str])`;
`set_active_language(x)` остаётся как частный случай на один элемент, чтобы не
трогать вызовы вне прогона. `overwrite_active_language` применяется ко всем языкам
прогона.

Слияние под `fcntl` и правило «объединять, никогда не удалять» не меняются.

### `translate.py`

`-l/--lang` принимает список через запятую: `-l pl,ko,ja`. Одно значение работает
как раньше. Коды проверяются по `config.languages` до запуска, дубликаты
схлопываются, порядок сохраняется. Число языков в запросе — это и есть длина
списка, отдельного параметра не нужно.

### Тесты

Обновляются шесть файлов, где `dst_language` передаётся позиционно или в
конструктор. Добавляются:

- разбор ответа на три языка → три словаря переводов;
- блок с неверной длиной → этот язык в отказ, два других применены;
- отсутствующий блок → то же самое;
- блок с чужим кодом языка → отброшен, прогон не падает;
- фраза, валидная в одном языке и пустая в другом, после батча не перезаписана в
  первом;
- `load_prompt` с невалидным промптом → исключение, а не пустая строка.

Снапшоты промпта (`tests/test_prompt_snapshot.py`) обновляются осознанно, через
`UPDATE_PROMPT_SNAPSHOTS=1`, дифф читается глазами и входит в тот же коммит.

## Готово, когда

Прогон на трёх языках раскладывает результат по трём `progress.json`, а
искусственный отказ одного из них оставляет два других переведёнными.

Плюс базовая линия держится: `uv run pytest -q`, `uv run ruff check .`,
`uv run mypy lib` — чисто.

## Что не входит

Словарь, опорные переводы, примеры-соседи (A2–A4), правила языка целиком (A5),
нарезка батча по выходу (A6). A6 идёт следом и опирается на число языков прогона,
поэтому A1 не должен зашивать `batch_max_tokens` в подсчёт по входу глубже, чем
сейчас.

Правка `scripts/tradusco/run-all.js` в t3, который сейчас гоняет локали
последовательно. После A1 он группирует локали в один запрос — отдельный коммит в
t3, после ядра.

`README.md`, `INTEGRATION_GUIDE.md`, `REWORK_PLAN.md` описывают «один язык за
прогон» и правятся одним коммитом после A1.
